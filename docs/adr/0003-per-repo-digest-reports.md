# ADR-0003: A per-repo digest layer, alongside (not instead of) portfolio-wide reports

- **Status:** Accepted

## Context

Every collector CSV already carries a `repo` column (`inventory.csv`, `complexity_hotspots.csv`,
`security_secrets.csv`, `testquality_runs.csv`, ... — the raw per-repo data has always been there).
But nothing in `synthesis/` or `reporting/` ever turns that into a report scoped to one repo.
`deep_reports.py`'s 15 `REPORT_SEQUENCE` functions, `exec_deck.py`'s 8 slides, and `report.py`'s
`REPORT.md` all take the same shape regardless of portfolio size: sort/slice "top N across the
whole target," or sum/count into one portfolio-wide number. Confirmed by direct read of all six
report-layer files (`deep_reports.py`, `exec_deck.py`, `synthesize.py`, `report.py`,
`pdf_export.py`, `core/util.py`'s `discover_repos`) — the only single-repo/portfolio branch in the
entire report layer is one `if/else` in `duplication_report`. `synthesize.py`'s `risk_ranking.csv`
comes closest (one row per repo) but a row is 8 scorecard numbers for cross-repo comparison, not
that repo's own hotspots/findings/failures.

This was never a deliberate call — neither ADR-0001 nor ADR-0002 weighs per-repo depth against
cross-repo synthesis. It's what fell out of generalizing the `chronicle_button` engagement's own
report set (`REPO_ANALYSIS.md`, `COMMIT_ONTOLOGY.md`, `EFFORT_ALLOCATION.md`, `ESCAPE_V2.md` — all
portfolio-wide even there) into `deep_reports.py`. That engagement had a *second*, separate
mechanism this generalization left behind: `analyses/DRILLDOWN_INDEX.md` →
`analyses/drilldown/<repo>.md`, one dedicated file per repo (103 of them), scoped to
testing-quality findings — e.g. `drilldown/buttonia.md` citing "the suite's content assertions are
broken and always pass (`notEqual(number, [-1])`, test.js:16-17)" for that one repo specifically.
That mechanism never made it into `repo_analyser`.

The result: pointing this tool at a 26-repo portfolio (`posx`) or a single repo (this tool
analyzing itself) produces the *same* kind of report either way — rankings and aggregates — with
no page that says "here is everything worth knowing about repo X."

## Decision

Add a **per-repo digest**: one consolidated markdown page per repo, plus an index, generated by a
new `synthesis/per_repo_digest.py` module (new pipeline step `per_repo_digest`, after `synthesize`
so it can cite that repo's risk rank, before `deep_reports`). Deliberately scoped **light**, per the
`chronicle_button` precedent above — one page pulling the most decision-relevant findings across
categories per repo, not a full per-category-per-repo matrix (15 categories × 26 repos = 390 files
for `posx` alone, and × 180 for the `button` portfolio — that explosion answers a question nobody
asked). Sections, in order: CI gate status, coding (complexity hotspots, lint, maintainability —
this repo's rows only), testing & mutation (this repo's own run + score), security (this repo's own
secrets/semgrep findings, real file:line), performance/latency budget (new dimension, ADR pending —
see `docs/ROADMAP.md`; the section renders `_not yet measured_` until that collector exists, per
ADR-0001's fail-loud-not-silent rule — never silently omitted), duplication involvement (is this
repo a party to a cross-repo clone or exact-duplicate group — direct input to "which components are
merge-into-a-shared-library candidates"), escape rate, dependency CVEs, and an "Honest limitations"
section matching `deep_reports.py`'s own convention.

This is **additive, not a replacement**: `deep_reports.py`/`exec_deck.py`/the main PDF are unchanged
and still answer "how does the ecosystem look as a whole" (duplication *between* repos, shared
dependencies, the risk ranking) — a question a per-repo page can't answer on its own. The two views
serve different questions; ADR-0004 would be needed to argue for merging or removing either one.

Output lands at `<out>/deep/per-repo/<repo>.md` + `<out>/deep/PER_REPO_INDEX.md` — markdown only for
v1 (matching the `chronicle_button` precedent, which was also markdown-only), not folded into the
existing PDF pipeline. `pdf_export.py`'s `REPORT_SEQUENCE`-ordered glob is untouched; per-repo files
live in their own subdirectory specifically so they're invisible to that glob rather than needing an
exclusion rule.

## Consequences

- New CLI module `per_repo_digest`, inserted into `cli.py`'s `MODULES` between `synthesize` and
  `trends`. Not in `SLOW_MODULES` — pure CSV/JSON reads, no subprocess calls, same as `synthesize`/
  `deep_reports` (`synthesis/` calls no external tools, per ADR-0002).
- A portfolio of *N* repos now writes *N* additional markdown files. For `button`-scale (180 repos)
  that's 180 small files plus one index — real but bounded (each file is one repo's own rows, not a
  cross product), and consistent with the actual precedent this generalizes from.
- A single-repo target (e.g. this tool analyzing itself) gets exactly one digest file. The existing
  portfolio-wide reports still run for a single-repo target too (they already degenerate gracefully
  to "top N of 1" tables, per the codebase's existing single-repo handling) — this ADR doesn't
  change that, it adds the one file that's actually useful in the single-repo case.
- `trends.py` (regression/improvement vs. the last run in the same `--out` dir) is untouched by this
  ADR. It currently diffs whatever `risk_ranking.csv`/portfolio-wide numbers already track; making it
  diff per-repo digest content across runs is a real, separate follow-up (see `docs/ROADMAP.md`),
  not assumed solved by this change.
- Repo names used as filenames come from `Path.name` (already the existing convention —
  `cli.py:100` passes `[r.name for r in repos]` to `synthesize` the same way), never a raw path
  component that could contain a separator — no new path-traversal surface.
